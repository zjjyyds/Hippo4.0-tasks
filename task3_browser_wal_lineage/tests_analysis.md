# Test 分析（供审核员阅读）

## 1. Instruction 和 Environment 的可见条件
真实 GitHub 源码固定到特定 commit。Agent 看到 `browser-forensic-core` 提供的 `wal_lineage` 公开接口和 stub，要求对 SQLite 主文件及可选 WAL 返回每次可证明的已提交数据库物理镜像的页数、提交帧号及 SHA-256；不可破坏证据、保持原有核心库行为，验证环境离线。不指定求解算法或调试步骤。

## 2. 模型理论通过路径
Agent 可阅读固定上游关于只读 SQLite 证据的现有实现，研究 SQLite 已公开的 WAL 持久化格式，从真实输入验证解析、事务可见性和连续镜像含义。可以通过任何符合最终输出要求的算法恢复结果。

## 3. Test 检查点及依据
- 有效 WAL 提交：必须正确报告每次提交帧号及数据库页数，对应 Instruction 的历史提交输出。
- 页镜像 SHA：通过整个重建镜像散列校验，防止只还原部分页面、只输出最后视图或硬编码特征。
- 页大小/重复重写/多事务：属于标准 SQLite WAL 语义及不同数据库的正常使用形态。
- 无 WAL、无效文件、截断和异常尾部：对应“只能输出证据可证明的提交、保留合法前缀、无法使用时返回空”要求。
- 随机化真实 SQL 事务和有效校验：避免通过固定输入/样本名猜答案。
- 原生核心库回归和原始证据不变：对接口与兼容性的检查。

**主要验收红线**：不检查 Agent 的工具、命令、代码组织、算法实现或结束时机；测试参考结果不打入 Agent 镜像。不利用隐藏的非标准 WAL 规则制造不可推断的失败。

# 第三题 V2：测试与机审分析

## 合约 / 质量审查
题面只规定输入证据布局、Rust 函数签名、输出字段、观察点顺序、五种证据关系的真值条件、损坏数据和文件不变性要求。没有建议具体 WAL 解析算法、checksum 端序公式、状态机划分、优先调试步骤、强制公测脚本或“测试通过就退出”的过程要求。

## 32 例独立场景
- 4 组 SQLite 页大小 × 8 类证据结构。每组采集数量 3～4，带独立随机主键、WAL 页载荷、文件名和 manifest 顺序。
- 真实继续写入、Checkpoint 后更换 WAL、位级相同副本、有效但冲突的 WAL、重签名独立 WAL、坏尾 + 恢复前缀、世代错配、截断/未提交帧与回退至历史中间提交的基底。
- 异常主文件 2 例；符合输出契约的错误必须被识别。
- 验证所有有序采集对，不仅检查相邻两份证据。关系 `checkpoint_compatible` 附带**全部**历史匹配提交帧（可以是中间提交）。

## Oracle 独立性
Python 参考逻辑基于原始物理格式计算提交镜像和证据关系，与 Rust 参考解法独立。再将每个已提交前缀交由真实 SQLite 引擎打开并执行 checkpoint，用主文件 SHA-256 独立复核。通过 3 × 32 例、348 份可恢复证据、804 个提交前缀。该交叉校验检验 SQLite 认可的物理状态，不应误称 804 个独立题型。

## 公开/私有边界
公开工程只有接口和 stub；`solution` 为 Oracle 参考补丁，`tests` 为私有随机化输入与评分器，容器通过不同路径和权限隔离。验证只比较最终 JSON 和证据文件哈希，不扫描模型源码或规定调试工作流。

## Baseline / 剩余风险
- NOP 等价空结果驱动真正 verifier：0/32、非零退出；完整通过制 reward 预期 0。正式编译 Rust starter 和 Harbor NOP 尚未执行。
- Rust 参考实现、Docker 环境及 Agent 五轮均尚未在本环境完成构建/试跑，不能宣称 Oracle 1.0、平均 80 轮或 Mean≤0.4。
- 额外风险：命题仍依赖公开 SQLite WAL 文件格式，领域冷门并不保证强模型难以完成；须观察第一轮真实解题轨迹再决定是否加难。
